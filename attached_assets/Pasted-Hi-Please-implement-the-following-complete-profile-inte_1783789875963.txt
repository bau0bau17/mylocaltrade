# PART 1 — Profile changes must require Admin review

Users may enter and edit their information normally before initially submitting their account/profile information.

After the relevant information has been submitted, the approved/current values must no longer be replaced immediately by user edits.

Instead, any later modification to a protected field must create a Profile Change Request for Admin review.

The current approved value must remain active until the proposed value is approved.

## Protected trader fields

Apply this workflow to:

- business/company name;
- contact name;
- phone number;
- website;
- business description.

## Protected customer fields

Apply this workflow to:

- personal/full name;
- phone number;
- any equivalent identity/contact field that currently exists in the customer profile.

Do not add unrelated fields to this workflow without checking with me first.

## Correct trigger for traders

For traders, the protection should begin when the trader profile/onboarding is submitted for review.

It should remain active while the profile is:

- Pending review;
- Approved/Verified;
- Live;
- undergoing re-verification.

Before the first submission, the trader can edit the fields normally.

After submission, changes to protected fields require Admin approval.

## Correct trigger for customers

Customers do not use the same trader-verification status, so do not incorrectly describe them as approved traders.

For customers, use the point when their initial identity/account details have been saved and the account is established.

After that point, later changes to protected identity and contact details must become Profile Change Requests.

Please explain in your completion report which existing customer lifecycle state you used as the technical trigger.

# PART 2 — Profile Change Request workflow

When a trader or customer proposes a change:

1. Keep the current approved value active.
2. Store the proposed value separately.
3. Create a Pending Profile Change Request.
4. Do not update the live/public/account value yet.
5. Show “Change pending review” beside the affected field.
6. Allow only an authorised Admin to approve and apply the change.
7. If approved, atomically replace the current value with the approved proposed value.
8. If rejected, keep the current value unchanged and show the rejection status and reason.
9. If more information is required, show the Admin’s instructions to the user.
10. Prevent multiple conflicting pending requests for the same field.
11. Protect the workflow at API/backend level, not only in the mobile UI.
12. Prevent users from bypassing the review through direct API requests.
13. Record a complete audit history.

The audit history should include:

- user/account;
- customer or trader role;
- affected field;
- previous approved value;
- proposed value;
- request timestamp;
- decision;
- Admin user;
- decision reason;
- decision timestamp;
- any request-for-information history.

Pending values must not appear in:

- public trader profiles;
- search results;
- trader cards;
- enquiries;
- conversations;
- public APIs;
- notifications to unrelated users.

# PART 3 — Phone-number changes and Twilio SMS/RCS verification

A proposed new phone number must be verified before it can be submitted to Admin.

Please reuse the existing “Check/Verify phone with SMS” flow from the trader Account Review / Trader Onboarding verification journey.

Do not create an inconsistent second phone-verification system.

The required flow is:

1. User selects Edit/Change phone number.
2. User enters the proposed new UK mobile number.
3. Show the same clear SMS/RCS consent wording used in the existing account-review phone-verification flow.
4. User actively taps “Send verification code”.
5. Backend sends a one-time verification code through the existing Twilio Verify integration.
6. Delivery should use SMS/RCS according to the existing approved/configured Twilio setup, with SMS fallback where RCS is unavailable.
7. User enters the six-digit one-time code.
8. User taps “Verify code”.
9. Backend verifies the code through Twilio.
10. Only after successful OTP verification should the proposed phone number be submitted as a Pending Profile Change Request.
11. The currently approved/verified phone number must remain active until Admin approves the change.
12. Successful OTP verification of the proposed number must not immediately replace the existing number.
13. If Admin rejects the change, retain the current approved phone number.
14. Do not mark the proposed number as the account’s active verified number before Admin approval.

Please confirm that the RCS delivery behaviour is genuinely supported by the current Twilio configuration. Do not claim RCS delivery if production currently falls back to SMS while the RCS sender is still pending approval.

# PART 6 — Contact details must remain hidden before quote acceptance/hire

The goal is to keep enquiries, discussions and structured quotes inside MyLocalTrade until the customer accepts a quote or hires a trader.

Before a quote is accepted or the trader is hired:

- Do not show the trader’s phone number to the customer.
- Do not show the customer’s phone number to the trader.
- Do not expose either party’s email address.
- Do not expose direct contact details through enquiry or conversation API responses.
- Do not show clickable phone or email actions.
- Communication should take place through the existing MyLocalTrade chat.
- Customers and traders must still be able to exchange job details and photos.
- Traders must still be able to send Structured Quotes.
- Customers must still be able to use Compare Offers.

The customer’s phone number may still be collected securely when an enquiry is submitted, but it must not be revealed to traders before hire.

The trader’s phone number may remain stored for verification and Admin use, but it must not be revealed to customers before hire.

# PART 7 — Contact details after quote acceptance/hire

After the customer accepts a Structured Quote or completes the existing Hire Trader action:

- Reveal verified contact details only to the customer and the hired trader.
- Show a clear “Contact details available” section in the hired-job conversation.
- Allow the customer to call the hired trader.
- Allow the hired trader to call the customer.
- Keep chat available and encourage users to document important job details and agreements there.
- Continue using the existing job-reference and hiring records.
- Do not expose contact information to traders whose quotes were not accepted.
- Do not expose the details in unrelated conversations.

Use the backend hire/accepted-quote state as the source of truth. Do not implement this only as a client-side visibility rule.

If a newly approved phone-number change is applied after a trader has already been hired, ensure authorised hired conversations receive the new approved/verified number and never the pending value.
