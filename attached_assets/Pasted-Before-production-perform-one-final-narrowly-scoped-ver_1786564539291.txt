Before production, perform one final narrowly scoped verification/fix. Do not redesign or expand the campaign system.

The hardening report currently states that every explicit Brevo 4xx response is treated as `waiting_quota`. That classification is too broad.

1. CLASSIFY BREVO FAILURES CORRECTLY

Implement and test distinct handling for:

- `not_enough_credits` or confirmed account-credit exhaustion:
  - `WAITING_FOR_QUOTA`
  - Recipients remain safely queued
  - Retry allowed after quota reset or plan upgrade

- HTTP 429:
  - `WAITING_FOR_RATE_LIMIT`
  - Respect `Retry-After` or Brevo rate-limit reset information where available
  - Do not describe this as daily/monthly credit exhaustion

- HTTP 400/422 or confirmed validation failure:
  - Permanent configuration/content failure
  - Do not retry automatically every day
  - Show the actionable Brevo error safely in Admin without exposing secrets or recipient data

- HTTP 401/403:
  - Authentication/permission/configuration failure
  - Do not mark as quota exhaustion
  - Admin must clearly say that the Brevo API key or permissions require correction

- HTTP 404:
  - Reconcile the missing remote list/campaign safely
  - Recreate only when it cannot duplicate a send
  - Otherwise require manual review

- HTTP 409/duplicate/conflict:
  - Reconcile with the stored Brevo IDs
  - Never create or send a duplicate campaign

- Explicit successful send:
  - Mark normally

- Ambiguous timeout/network loss/5xx after the send command may have reached Brevo:
  - Preserve the conservative no-resend/assumed-sent behaviour
  - Clearly mark it for manual verification in Brevo

Do not expose raw Brevo response bodies if they contain private data.
