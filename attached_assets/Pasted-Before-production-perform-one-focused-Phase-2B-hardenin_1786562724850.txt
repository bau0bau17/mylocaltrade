1. BREVO TEMPORARY LIST LIFECYCLE

The implementation creates a unique Brevo contact list for every batch. Brevo has a finite contact-list quota, so these lists must not accumulate indefinitely.

Inspect the exact lifecycle.

Implement safe cleanup for temporary batch lists after:

- The Brevo campaign has been created/sent
- The local immutable recipient snapshot is preserved
- Any information still needed for webhook matching is stored locally
- Deleting the list no longer risks affecting an active send

Store cleanup state and make cleanup idempotent.

A failed cleanup must be retryable without resending the campaign.

Add an Admin warning/status for orphaned Brevo resources if cleanup repeatedly fails.

Do not delete the local campaign, recipients, audit history or Brevo campaign reference.

Add tests proving that repeated batches do not permanently consume one Brevo list each.

3. WEBHOOK AUTHENTICATION

Do not place `BREVO_WEBHOOK_SECRET` in the query string.

Use Brevo’s supported webhook authentication or a dedicated custom authentication header, such as an Authorization header or a clearly named custom header.

The server must:

- Validate the header using constant-time comparison
- Reject missing/invalid authentication
- Never log the secret
- Not accept authentication only from a URL query parameter in production
- Support safe secret rotation if practical

Update the final manual Brevo setup instructions with the exact header/authentication configuration.

4. GLOBAL TEST-EMAIL LIMIT

The current limit of 5 test emails per campaign is not sufficient by itself because Brevo’s campaign test-email allowance is global per account/day.

Add a globally serialised database-backed test-send counter across all campaigns and administrators.

Keep both limits:

- Maximum 5 test sends per campaign per day
- Maximum configurable global test sends per day, with a safe default below Brevo’s documented account limit

Test sends must also be included in the local email-credit accounting where appropriate.

Concurrent test-send requests must not exceed either limit.

5. DAILY CREDIT FAILURE BEHAVIOUR

The local 200/100 split is a conservative allowance, not proof of Brevo’s actual remaining credits after transactional sends.

Make this limitation explicit in the Admin interface and final report.

Handle Brevo responses carefully:

- If Brevo explicitly returns `not_enough_credits`, do not mark recipients as sent or assumed sent.
- Move the batch/campaign to `WAITING_FOR_DAILY_QUOTA`.
- Preserve recipients for a safe retry after the quota resets.
- Release or correct any unused local reservation safely.
- Do not create a duplicate campaign on retry if Brevo already created one.

Only use an `assumed sent`/no-retry outcome when the result is genuinely ambiguous after a send command may have been accepted, such as a timeout or connection loss after submission.

Add separate tests for:

- Explicit insufficient-credit rejection
- Rejection before campaign creation
- Campaign created but send rejected
- Timeout after send request
- Safe retry next day
- No duplicate delivery
